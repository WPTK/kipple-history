# 1.1 bug-hunt research

Outside research gathered 2026-10-17 for the 1.1 bug-hunt plan ([plans/1.1-bug-hunt-plan.md](../plans/1.1-bug-hunt-plan.md)). Sources are linked inline. Where a search came back thin, the text says so. Practices from other projects ("in CI", "scheduled", "gate", "budget") are not adopted: everything here is run by hand for this version.

## Additions from outside research
Reading note (owner ruling): wherever the research below says "in CI", "scheduled", "gate", "budget" or "fail the
build", that is how other projects do it and is NOT adopted here. Everything is run by hand for this version (see the
rules block); keep-it-permanently proposals go to `roadmap` issues.

Scope correction (owner): the release clears **P0-P4** bugs, not P1-P4. Applied throughout. The memory file
`plan-1-1-bug-hunt-tooling.md` still says P1-P4 (plan mode blocked editing it); fixing it is the first thing to do
once plan mode ends, along with adding the phase list to it. Check the label set has P0 (memory
`github-label-taxonomy`).

**Fuzzing**
- Commit crash reproducers in `testdata/fuzz/<Name>/` so plain `go test` replays them on every PR; seed with `f.Add`.
- Two-tier setup per [ClusterFuzzLite](https://google.github.io/clusterfuzzlite/): short fuzz on PRs, long scheduled
  batch fuzz that builds the corpus. It supports Go. Cache and periodically minimize the corpus between runs
  ([corpus management](https://tessl.io/registry/testland/coverage-guided-fuzzing/files/references/corpus-management.md)).
  Search results were thin on Go specifics: check go.dev/doc/fuzz before wiring it up.

**Feed corpus and parser tests**
- Model it on Universal Feed Parser: well-formed and ill-formed directories; ~960 real-world samples
  ([bozo detection](https://feedparser.readthedocs.io/en/stable/bozo.html)). Assert partial data is recovered plus
  an "ill-formed" signal, not just "no panic".
- Add resource-limit cases (max entries, nesting depth, oversized items), per
  [feedparser-rs](https://docs.rs/crate/feedparser-rs/0.7.0).
- Encoding fallbacks and mislabeled charsets ([Brent Simmons on Postel's law](https://inessential.com/2004/01/14/more_details_about_postels_law_atom.html)).
- Real-world defects list: obsolete EST-style timezones, missing dates, malformed authors, bare `www.` links, URLs
  with spaces, garbage bytes; plus parse, write, reparse stability ([SimpleFeed](https://www.nuget.org/packages/SimpleFeed)).

**SQLite / WAL**
- Crash-recovery test modeled on SQLite's [walcrash.test](https://gitea.com/package/sqlite/src/branch/master/testdata/tcl/walcrash.test):
  child process writes in WAL mode, kill it at random points with a fixed seed, reopen, run `PRAGMA integrity_check`,
  confirm `journal_mode` is still wal, check app invariants. In Go: `os/exec` + `TestMain` re-exec.
- Windows WAL startup crash in modernc.org/sqlite v1.38.0+ ([issue 221](https://gitlab.com/cznic/sqlite/-/issues/221)):
  check which modernc version Kipple ships and whether the Windows build is in the test matrix.
- `goleak.VerifyTestMain` for leaked goroutines from unclosed `*sql.DB`/`Rows` (general practice, not sourced).

**Concurrency tests**
- Go 1.25 `testing/synctest` gives a fake clock in a "bubble", replacing `time.Sleep` waits and removing timing flakes
  ([Applied Go](https://appliedgo.net/spotlight/go-1.25-the-synctest-package/)). Directly relevant to the one web
  timing failure and any scheduler/backoff tests. Check the final API names in the Go docs.
- Not covered by search: NilAway (Uber) and `fieldalignment` (x/tools); check their repos before adding.

**Web / accessibility**
- Automated axe catches only a fraction of issues (sources say about 30-40%), so keep NVDA keyboard/screen-reader
  passes and visual checks ([accessibility guide](https://dev.to/bugnificent/the-ultimate-guide-to-web-accessibility-testing-from-screen-readers-to-lighthouseci-2oa4)).
- Lighthouse CI set to fail, not warn; run it after E2E and accessibility jobs.
- Mutation testing (gremlins for Go, Stryker for TS): run on a schedule or on changed files, treat the score as a signal
  for test quality, not a standalone gate. Stryker details were not found in search.
- Practical sanity check: deliberately break something and confirm a test fails.

## Wider research: performance, UI, UX and user issues
Goal is every class of problem, not only crashes. Constraints from CLAUDE.md applied: no monitoring/telemetry (so lab
measurement only, no RUM), no Fever, test the protocol not named apps (reference servers are fine as a differential
baseline in tooling, never in user-facing text), nothing special per client app.

**Performance (backend)**
- `benchstat` (`go install golang.org/x/perf/cmd/benchstat@latest`): run benchmarks `-count=5+` and compare before/after;
  use `b.Loop()` (Go 1.24+); CPU/alloc/trace profiles with pprof and `go tool trace`
  ([guide](https://tessl.io/registry/skills/github/samber/cc-skills-golang/golang-benchmark)).
- Continuous benchmark in CI, fail only on statistically significant regressions; shared runners are noisy, so keep
  the baseline run on one stable machine ([GitHub Actions approach](https://dev.to/vearutop/continuous-benchmarking-with-go-and-github-actions-41ok)).
- Candidate benchmarks: feed parse, sanitize, FTS search, mark-all-read on a big library, retention trim, OPML import
  of 100s of feeds, thumbnail pipeline memory. Use the existing `scripts/scalegen` for library size.
- PGO (`default.pgo`, Go 1.21+) is optional; only if benchstat shows a real win (unsourced, verify in Go docs).
- Load: vegeta (installed) and k6 (`GrafanaLabs.k6`) against a seeded instance; look at p95/p99 and memory, not averages.

**Performance (frontend)**
- Interaction latency (INP): record slow interactions in DevTools Performance with 4-6x CPU throttling; the
  `web-vitals` attribution build splits input delay / processing / presentation
  (a performance checklist, not linked). Good INP is
  at or under 200 ms; confirm current thresholds on web.dev.
- Bundle size: `npx vite-bundle-visualizer`; add a size budget check to CI; lazy-load routes and heavy libraries.
  (`rollup-plugin-visualizer`/`size-limit` not covered by search; check their READMEs.)
- Long article lists: virtualization (TanStack Virtual or react-window); profile before adding memoization.
- Lighthouse CI as a failing gate for performance budgets, run after E2E and a11y jobs.
- Slow and offline networks: Playwright `offline: true` context; slow-3G profile needs Chromium CDP emulation (verify).

**UI / visual**
- Playwright `toHaveScreenshot` across projects for chromium, firefox, webkit and device profiles (mobile preset +
  desktop, matching CLAUDE.md's UI rule). Set tolerances globally (`maxDiffPixelRatio` ~0.005-0.02), mask dynamic
  content, fixed viewport, same browser versions and timezone/locale; baselines per browser per OS; update
  baselines only in reviewed PRs and upload diffs as artifacts
  ([guide](https://testdino.com/blog/playwright-visual-testing)). Matters here: 20 themes, many fonts, day/night.
- Breakpoints to cover: 320, 375, 428, 768 px plus orientation changes
  ([mobile emulation](https://www.mintlify.com/microsoft/playwright/guides/mobile-emulation)).
- Emulation is desktop engines with phone settings, so real iOS Safari/Android Chrome still need a pass by hand; a
  device cloud ([LambdaTest](https://qodex.ai/blog/browserstack-alternatives), TestingBot) is the paid fallback.
  Gestures (swipe/pinch/long-press) are not in Playwright's touch API beyond tap; CDP-only on Chromium (verify).
- Themes: contrast check on all 20 schemes via axe (color-contrast) per scheme; fonts: fallback and FOUT checks.

**UX and real-user issues**
- Heuristic evaluation (Nielsen's 10) by 3-5 independent passes (can be separate reviewer agents with different
  personas: first-run self-hoster, daily reader on phone, importer from another reader, keyboard-only,
  screen-reader user); combine findings ([overview](https://app.uxcel.com/glossary/heuristic-evaluation)). Findings
  differ from automated tests and from user testing.
- First-run and install friction (search found little; treat as our own checklist): fresh `docker compose` from the
  published example, setup wizard, restore flow, OPML import of the real files above, empty states, error messages
  that say what to do next, resumable flows, state persistence.
- Dogfood diary: owner and Claude each use it as the daily reader for a week; every papercut becomes an issue with a
  P-label. Also mine existing closed issues for repeat classes.

**Reader API (protocol) bug classes** (from the documentation of three open source implementations of the protocol: public notes on the Google Reader API).
- Auth matrix (API password vs web password, wrong creds, API disabled); escaped `%2F` in paths; base URL without API path.
- State changes on removed/trimmed items must still return OK so client sync does not stall (relevant to retention trim).
- Paging: `n` limits, continuation, date filters on item-ID calls; large unread counts.
- Feeds with only GUID permalinks, odd dates; CORS preflight and Basic auth for browser clients.
- Method: record real client traffic and replay it; differential run of one scenario against two reference servers,
  classify differences as bug or documented deviation.

**Security (beyond govulncheck/Trivy)**
- gosec + staticcheck + golangci-lint (installed); Semgrep for code patterns; CodeQL if enabled on the repo (not
  researched); Trivy already in `-Docker` CI; Dockle for image lint (not researched).
- Live app: ZAP (discovers surface, authenticated) and Nuclei (known issues) against a seeded instance behind the
  real Access setup; neither tests per-user authorization or logic, so keep the manual review
  ([comparison](https://falcao.org/posts/open-source-sast-dast-sca-2026/)). Security report stays private
  (both repos public); neutral public wording per memory.

**Test-suite health**
- Mutation testing (gremlins Go, Stryker TS) on scheduled/changed files; flaky-test tracking (the web `npm test`
  timing failure); `synctest` for time-based tests; run the full suite with `-race` and `-shuffle=on`, `-count=3`.

**Process**
- Phase it: (1) install + baselines, (2) automated sweeps (fuzz, race, static, security, perf baseline), (3) UI/UX
  sweep with personas, (4) triage everything into P0-P4 issues, (5) fix by theme with the 3-round review cap,
  (6) rc, soak, release. One writer per machine; no heavy tests in Docker on the dev machine.
- Done-when: zero open P0/P1; P2+ either fixed or deferred with an issue; benchmarks and visual baselines checked in.
