# Plan: 0.8.0-beta.1, 1.0.0-rc.1, 1.0.0

## Owner rulings (do not relitigate)
- **Not in scope, ever:** podcasts and media players, read-later or webhook integrations (Wallabag, Readwise,
  Instapaper), tags. These join the non-goals in CLAUDE.md. Kipple is not trying to match what every reader has.
- **No per-reader migration guides.** People can work it out; one sentence in the import docs says what an OPML
  file carries (feeds and folders) and what it does not.
- **Nested folders are a fix we need.** OPML import flattens them today (docs/design.md, "Single-level folders").
- **Stars and read state from other readers:** only if some reader's export carries them and a generic import is
  cheap; otherwise say so in one line. A research task decides.
- Before 1.0 nothing else is added. User-chosen Google Fonts waits for 2.0.0; the rest is in the roadmap tracker.

## Version path (the agent's call, as the owner delegated)
`0.8.0-beta.1` (nested folders, the one behavior change, plus the docs and hardening below), then `1.0.0-rc.1`, then
`1.0.0`. A candidate for 1.0.0 is named `1.0.0-rc.N`, not `0.8.0-rc.N`, and a release candidate adds no features,
so the nested-folders change lands in a beta. `0.8.0` never ships as a stable release (as with 0.5.0). If the folder
design turns out to need no schema or Reader API change and is small, the agent may fold it into `1.0.0-rc.1`
instead and say why in the PR; the rc rule (bug fixes only) is the test.

## Autonomy rules for the unattended window
The agent may, without asking: create branches and worktrees, commit, open PRs, merge to `main` when CI is green
on the exact head (one PR at a time, merging the base in, never force-pushing), file and label issues, run
subagents (Sonnet by default, Opus for design and whole-diff review, never Haiku), update the history repo
(fetch first, scrub rules) and open and merge website PRs for version text and, when the UI visibly changed,
screenshots.
The agent may NOT, without the owner's word in chat: push a tag, create a GitHub release, copy data off the
Kipple server, deploy, or touch the Kipple server's containers or compose file (including a rollback drill there).
If a command is denied, stop that item, keep the exact command in a scratch note for the owner and carry on with
unrelated work. Never route around a denial.
When the owner returns the first message is: what merged, what is queued behind his go (tag, release, backup,
deploy), and the decisions he must make.

## Reducing the overdoing (and what the effort taught us)
What the heavy gates caught, from the diary and challenges: the Opus whole-diff reviews found real defects on every
large diff (the 0.6 integration, the setup-code removal, the open-mode rule, the timing-test replacement); fuzz and
Suite 1 found nothing on the last four releases; the wall-clock tests were the only flake. So the rule becomes
**gates scale with what changed since the last gated commit**:
- **Docs, test-only, release-commit, dependency or log-line changes:** CI green on the exact head, govulncheck for
  any dependency change, and nothing else. No fuzz, no Suite 1, no review.
- **Code that parses, authenticates, migrates or renders UI:** the full set once, on the commit being tagged: two
  Go runs, fuzz, Suite 1, and an Opus whole-diff review. Not on every rc patch.
- **Soak:** one soak at the release candidate (a few days, the owner's real use, zero new P0/P1) after the beta's
  own soak. The "second soak and go/no-go meeting" becomes a written 1.0 readiness checklist
  (`docs/release-checklist.md`) that the owner signs off with one yes; one person does not need a meeting.
- **Website:** version text on every release (a one-line PR); screenshots only when the UI visibly changed.
- **Badges, hand-run steps:** no new badges; hand-run steps stay only where nothing else covers them.
Keep, because they paid for themselves: tag only on the exact green commit, the off-box copy before a deploy,
migration rehearsal on a copy of the live snapshot (Suite 4), the Opus review of large diffs, the deterministic
tests rule.

## Work packages (issues under milestone "1.0.0 - Stable"; tracker #179)
A. **Nested folders** (the one feature). Design twice first (an Opus agent): how the model, the Reader API (flat
   labels; how Reeder and NetNewsWire show or expect nesting), OPML import and export, the UI and the settings all
   represent a hierarchy; decide the data model and the Reader API mapping; say what restoring an old backup does.
   Then implement, review, test (unit, fuzz seed, UAT, real clients when the owner can), as a short PR chain.
B. **Portability research** (read-only): which readers export stars or read state, in what format, and whether a
   generic import is cheap. Output: a recommendation and, if cheap, an issue.
C. **Docs for strangers** (docs only): the compatibility and deprecation promise (what is public API: the Reader
   API, backup format, settings keys, environment variables, CLI subcommands, image tags, volume layout; what is
   not; "downgrade means restore"; which versions can migrate); SECURITY.md for 1.x; a troubleshooting and FAQ
   page and two or three reverse-proxy snippets; system requirements; a database growth and VACUUM note; a
   support-expectations paragraph; the non-goals including podcasts and read-later; issue templates; the pull
   compose example brought level with the build example (memory and pids limits, log rotation); a known-issues
   section in release notes; a table of contents in deploy.md.
D. **Security evidence** (tests and one workflow change): an SSRF matrix over every URL-taking entry point
   (alternate IP notations, IPv4-mapped IPv6, mixed DNS answers, non-http schemes, redirects to private hosts, the
   Reader API subscribe path, OPML import); a sanitizer regression corpus; verify (not assume) the absolute session
   cap, password reset revoking all sessions, and logout deleting the server row; an SBOM attached to the GitHub
   release by the release workflow; a one-page threat model and pentest checklist; `gh attestation verify` in the
   docs. Findings that are real bugs become fix PRs before the beta is tagged.
E. **Scale and baselines:** a synthetic large seed (feeds and 100k or more items) run natively on the dev machine,
   no Docker there: record startup, migration time, search, memory and database size in `docs/`; run the newest
   migration and an old-format backup restore on that data. Anything that fails is a bug fix.
F. **Compatibility checks:** Playwright projects for Firefox and WebKit in Suite 1 where they run; an automated
   keyboard-only pass. The manual screen-reader pass and Reeder and NetNewsWire on his phone stay with the owner.
G. **Process:** `docs/RELEASING.md` and CLAUDE.md updated for the rules above, the podcast and read-later
   non-goals, and `docs/release-checklist.md`.
H. **Bookkeeping, as normal workflow:** history repo updated after every merge batch and at least daily; website
   version text and, after A, screenshots; memory updated.
